The problem

One computer is a single point of failure.

If the only machine holding your data crashes, your app goes down. If its disk dies, the data is gone. Keeping copies on several machines fixes that, but creates a harder problem: how do they agree on what the data is when messages are lost and machines fail mid-update?

Without raftkv

One copy, one crash away from loss

A single server takes every write. When it fails, everything stops, and unsaved changes vanish.

With raftkv

Three copies that agree on every change

Every write is confirmed by a majority before it counts. Lose any one machine and the other two carry on.

How it works

Three ideas, no magic.

raftkv implements the Raft consensus algorithm, which is also what powers Kubernetes' etcd, CockroachDB and TiKV. Everything below is code written for this project, not a library.

Elect a leader

One machine leads and sends a heartbeat every 50 ms. If the others stop hearing it, they vote in a new leader. A machine wins only with a majority, and only if it already has all saved data.

raft/raft.go · terms, randomized timeouts

Agree before saving

Every write goes to the leader, which copies it to the others. It counts as saved only once two of the three machines have written it to disk, so a single failure can never erase it.

replication · group commit · write-ahead log

Recover automatically

A crashed machine reloads its log from disk when it returns, then receives whatever it missed, or a compact snapshot if it fell far behind. Nobody has to fix anything by hand.

Proof

We crashed it on purpose. Here is what happened.

For 90 seconds, a script froze, crashed and disconnected a machine every few seconds (12 failures in total) while a client kept writing. This is the monitoring dashboard from that run.

  1. Who's in charge (top left). The data is split into three slices; when machines failed, node 3 took charge of all of them.
  2. Writes per second (top right). The yellow line is successful writes, and it never stopped.
  3. Response time (bottom left). Brief spikes to 220 ms during handovers, then back to normal on its own.
  4. Elections (bottom right). Each step is a new leader being voted in. 29,463 writes succeeded; no saved data was lost.
